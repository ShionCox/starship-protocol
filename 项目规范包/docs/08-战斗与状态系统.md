# 15. 战斗系统需求

## 15.1 战斗阶段

```ts
type BattlePhase =
  | 'PREPARING'
  | 'COUNTDOWN'
  | 'ACTIVE'
  | 'ENDING'
  | 'RESULT';
```

## 15.2 每 Tick 推荐顺序

```text
01 读取 Command
02 更新能源
03 执行 AI 条件判断
04 生成 AI Command
05 更新船员任务
06 更新寻路
07 更新房间操作员效果
08 更新武器装填
09 创建 Projectile
10 更新 Projectile
11 命中/闪避判定
12 护盾结算
13 房间/船体/船员伤害
14 状态效果
15 火灾
16 医疗
17 维修
18 死亡
19 胜负判断
20 输出 Event
21 生成 State Hash
```

顺序一旦发布不得随意修改，修改必须升级 `battleRuleVersion`。

# 19. 火灾和状态效果

## 19.1 通用 StatusEffect

```ts
interface StatusEffect {
  id: string;
  type: string;
  sourceId: string;
  targetId: string;
  startTick: number;
  durationTicks: number;
  stack: number;
}
```

R1 状态：Fire、EMP、Healing、RepairBoost。

R2+ 可增加 Poison、Freeze、Stun、ArmorBreak、ReloadBuff、EvasionDebuff。

所有状态以 Tick 为单位。

## 19.2 R1 手动维修纵切

- 本阶段只实现已有房间耐久的恢复，不实现命中、伤害、火灾、维修能源消耗或 AI 调度。
- 工程师必须已在受损房间且处于空闲状态，玩家通过显式 Command 开始或停止维修。
- 每 Tick 先推进船员移动，再按稳定船员实例 ID 结算维修；多名工程师可叠加，房间耐久封顶后所有相关维修任务自动结束。
- 维修 Tick 位于完整战斗顺序的第 17 步；医疗仍位于第 16 步。本纵切尚未建立完整 Battle Tick，因此不得据此改变已发布战斗顺序。
- 当前维修不消耗能源；后续房间状态和能源惩罚切片再接入该规则。

## 19.3 R1 手动供电医疗纵切

- 本阶段只处理场景预设的船员低生命，不实现真实伤害、死亡、医疗 AI、自动返岗或医疗物资。
- 玩家先把病员移动到已供电医疗室；应用层选择同房间最低实例 ID 的空闲医务员，再发送包含病员、医务员和医疗室 ID 的显式 Command。GameCore 不自行猜测医务员。
- 每 Tick 先推进所有移动任务，再按稳定医务员实例 ID 结算医疗，最后按稳定工程师实例 ID 结算维修。医疗室的 `healingHpPerTick` 决定恢复量，病员生命封顶后双方自动空闲。
- 医疗室必须达到定义的最低能源。断电立即解除该房间全部治疗配对，双方恢复 `IDLE`，之后不会继续恢复生命。
- `HEALING` 与 `TREATING` 必须通过 `taskPartnerCrewId` 双向配对、同房且不同实例；非法配对快照整份拒绝。
- 本纵切对应完整战斗 Tick 的第 16 步医疗，维修仍是第 17 步；尚未建立完整 Battle Tick，不改变已发布顺序。
