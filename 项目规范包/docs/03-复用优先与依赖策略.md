# 复用优先与依赖策略

> **目的**：减少重复组件、重复服务、重复工具和不必要的自研基础设施。  
> **原则**：项目特有玩法可以自研；通用能力优先复用 Cocos、标准库、既有模块或成熟第三方库。

## 1. 复用决策顺序

每次准备新增“通用能力”时，按以下顺序判断：

```text
已有项目模块
    ↓ 没有
Cocos 内置能力
    ↓ 不满足
JS / TS 标准能力
    ↓ 不满足
成熟且兼容的第三方库
    ↓ 不满足
最小范围自研
```

任何跳过前四步直接自研的通用能力，都需要在代码评审中说明原因。

## 2. Cocos 能力优先表

| 需求 | 默认方案 | 不建议 |
|---|---|---|
| 节点/生命周期 | Node + Component | 自建第二套实体生命周期 |
| UI 对齐 | Widget / Layout | 自己手写完整布局引擎 |
| 按钮 | Button + 项目皮肤封装 | 每个页面各写点击状态机 |
| 滚动 | ScrollView | 每页自建滚动容器 |
| 裁切 | Mask | 自写通用裁切系统 |
| 动画过渡 | tween / Animation | 再引入一套只做简单 Tween 的系统 |
| 资源复用 | Prefab + instantiate | Scene 中手摆大量重复节点 |
| 资源分包 | Asset Bundle | 自建第二套资源清单/下载框架 |
| 图集 | SpriteAtlas | 每个小图单独加载 |
| 音频 | Cocos Audio 能力 + AudioService薄封装 | 多套音频管理器 |
| 输入 | Cocos 输入事件 + InputMapper | 页面各自监听物理按键 |
| 场景 | Cocos Scene + 少量主场景 | 每个页面都做 Scene |
| 单个资产的编辑器预览/吸附 | Prefab + `executeInEditMode` + Node 变换事件 | 自建第二套场景编辑器 |
| 批量内容创建/校验/导出 | Cocos 项目扩展 + 公开 Panel/Asset DB/Scene 消息 | 手改序列化文件或每个领域各建插件 |
| Windows HTTPS/签名/Hash | WinHTTP + WinTrust + BCrypt + Crypt32 | 在客户端引入第二套通用密码库 |

## 3. 哪些能力适合项目自研

以下属于项目核心竞争力或存在特殊确定性要求，可以自研：

- 飞船网格与不规则船体占用；
- 房间放置验证；
- 船舱导航图；
- 船员任务调度；
- 固定 Tick 战斗；
- Seeded RNG；
- 条件 AI 规则解释器；
- Command / Event / Snapshot；
- Replay / Checkpoint；
- 战斗状态 Hash；
- 配置版本迁移；
- 服务端权威校验。

## 4. 统一封装，而不是重复实现

### 允许的做法

在 Cocos 能力外面做**薄封装**，用于统一主题、错误处理和项目约定，例如：

```text
GameButton -> 封装 Cocos Button
GameScrollView -> 封装 Cocos ScrollView
AudioService -> 统一调用 Cocos 音频能力
AssetService -> 统一调用 Asset Bundle
InputMapper -> 将鼠标/触摸/键盘映射为游戏 Action
```

### 禁止的做法

- `GameButton` 内重新实现完整的按钮事件系统；
- `GameScrollView` 完全绕过 ScrollView 再造一套滚动；
- `AssetService` 自己再设计一套和 Asset Bundle 平行的生命周期；
- 每个业务模块都创建自己的 EventBus。

## 5. VirtualList 规则

Cocos ScrollView 负责滚动和裁切；**虚拟化**属于项目性能适配层。

项目只允许存在一套通用：

```text
VirtualList
VirtualGrid
```

业务页面通过 `ItemRenderer` / 数据绑定适配，不得再复制第二套“背包虚拟列表”“船员虚拟列表”“商店虚拟列表”。

## 6. 第三方依赖引入标准

引入第三方库前必须确认：

- 是否支持 ESM；
- 是否不依赖 Node.js 内置模块（客户端共享包）；
- 是否不强依赖 DOM；
- 是否兼容 Web；
- 若未来需要 Native，是否有替代/适配方案；
- 包体是否合理；
- 维护状态是否可接受；
- 是否真的比 30～100 行项目特有代码更合适；
- 是否会破坏确定性或 Replay 兼容。

新增依赖时在 PR/提交说明中写清“解决什么问题、为何不用现有能力”。

## 7. 服务/管理器唯一性

以下能力全项目原则上只能有一个正式入口：

```text
Logger
AssetService
AudioService
InputMapper
HttpClient
WebSocketClient
PopupService
ToastService
Clock / TickScheduler
SeededRandom
ConfigRegistry
ReplayCodec
```

业务层可以有 Adapter，但不能各自另起一套核心实现。

## 8. 搜索优先

GPT / Codex 新增文件前应先搜索：

- 文件名相近；
- 类名相近；
- 接口职责相近；
- `Manager` / `Service` / `Utils` / `Helper`；
- 相同事件名；
- 相同配置 key；
- 相同 DTO。

发现已有实现时，优先组合、扩展或重构现有实现。

## 9. 什么时候允许“自己造”

满足以下任一条件可以自研：

1. 玩法规则是项目独有；
2. 需要严格确定性；
3. 现有方案不兼容 Cocos/Web/Native；
4. 第三方库体积或依赖树过大；
5. 外部库无法满足性能要求；
6. 外部库的授权不适合项目；
7. 封装成本已经接近直接实现成本。

即使自研，也只实现项目实际需要的最小能力，不做“未来可能用到”的通用框架。

项目编辑器扩展属于 Cocos 官方能力上的薄适配：宿主只聚合真实存在的资源菜单和唯一创作面板；房间、NPC、关卡保留各自模型，不建立万能 EntityEditor。场景修改只复用公开 Panel、Selection、Scene/Asset DB 消息；禁止依赖未公开的 hierarchy 注入、`cce.*` 或 DOM 补丁。

Windows 正式发行安全同样采用平台薄适配：启动器复用系统 TLS、代码签名和密码 API；Node 发布工具只使用 `node:crypto`。不得为了相同算法在 GameCore、Cocos View 和插件中各写一套密码实现。
